## 2. Как запускать и тестировать
- Превью: `preview_start("habits-static")` → вернёт `serverId`. Это static-сервер на :4599.
- Паттерн теста: положить в `localStorage['habbittracker_progress']` JSON-стейт (см. §3),
  `location.reload()`, потом гнать через `preview_eval` / `preview_screenshot`.
- **В конце всегда** сбрасывать: `localStorage.removeItem('habbittracker_progress')`.
- Машинные часы превью идут по РЕАЛЬНОМУ времени (дрейфуют между сессиями). ВСЕГДА сверяй
  `new Date()` / `todayKey()` перед сидированием дат — НЕ хардкодь конкретный день.
- Перед концом правки: `node --check habbittracker.js`, баланс тегов в HTML, скриншот
  изменённого вида, проверка `preview_console_logs` (level error), сброс localStorage.

### Грабли (проверено на практике)
- **Скриншот ловит транзишн вкладок** (0.2s): активная вкладка может выглядеть не-чёрной
  сразу после клика. Это артефакт — переснимай позже, а состояние читай через `eval`
  (`getComputedStyle` тоже может вернуть промежуточное значение анимации).
- **CSS иногда кэшируется** при reload — полный `location.reload()` подхватывает изменения.
- **reload внутри `preview_eval` обрывает промис** ("Inspected target navigated") — делай
  reload отдельным вызовом, потом следующий eval.
- Свежий поток: интро ~2000ms (loading 1500 + fade 500), тур стартует +700ms → ~2.7s после
  тапа по интро.

## 3. Модель данных — `dashState` (ключ `habbittracker_progress`)
```js
{
  level, currentXP,
  habits: [{ uid, text, completed, xpDate?, areas:[areaId...], triggerText?, reminderTime? }],
  unlockedGames: [gameId...],      // [] у нового → выбор ПЕРВОЙ игры; +1 на ур.3/7/10
  lastActiveDate,                  // 'YYYY-MM-DD' (UTC, как в checkNewDay)
  checkins: { morning:{}, evening:{} },               // черновик чек-апов на сегодня
  checkinHistory: { 'YYYY-MM-DD': { morning:{...}, evening:{...} } },
  history: { 'YYYY-MM-DD': { uid:true } },             // ВЕЧНЫЙ лог выполнения привычек
  foodLog: { 'YYYY-MM-DD': { breakfast:{time,text}, lunch:{...}, dinner:{...} } }, // вкладка Питание
  psychoMode: false,
  metrics: [{ id, name, type:'goal'|'limit', target, unit?, step? }], // ЖИВОЙ список метрик (юзер CRUD-ит)
  metricTargets: { metricId:number },                 // переопределённые цели метрик (override target)
  metricLog: { 'YYYY-MM-DD': { metricId:number } },
  onboardingDone: bool,
  seenHints: { month?, morning?, evening?: true }
}
```
**Даты:** `history` и `metricLog` ключуются ЛОКАЛЬНО через `fdt(y,m,d)` =
`` `${y}-${pad(m+1)}-${pad(d)}` ``. `checkinHistory` местами ключуется UTC
(`toISOString().split('T')[0]`). График настроения/сна читает с дабл-фолбэком local→UTC.
Это намеренная совместимость со старым кодом — не «чини» бездумно.

`checkNewDay()` на новый день обнуляет `habits[].completed` и `checkins`, но НЕ трогает
`history`/`checkinHistory`/`metricLog`.

**Миграция метрик (init):** проверяй именно `saved.metrics`, НЕ `dashState.metrics` — у скелета
`dashState` теперь `metrics:[]`, поэтому после слияния отличить «старый сейв без метрик» от «юзер
удалил все метрики» можно только по сырому `saved`. `!Array.isArray(saved.metrics)` → сидируем 7
дефолтов; `saved.metrics:[]` (пустой) → оставляем пусто. (Старые `calories`/`claude` в `metricLog`
остаются осиротевшими — безвредно, не рендерятся.)

## 5. Что построено (фичи и где)

видов), вызывает рендер вида + `maybeShowViewHint(view)`.

**Нижний кластер зафиксирован (мобильная адаптация):** `#psycho-toggle` + `.view-switcher` +

`.dash-content` резервирует место под него через `padding-bottom: var(--bottom-bar-h)`; высоту
меряет `measureBottomBar()` (habbittracker.js, вызывается на старте + resize + два отложенных
ремера 300/1200мс на случай позднего reflow от шрифтов). Не хардкодь `padding-bottom` — высота
зависит от переноса текста на узких экранах.
**Свайп между вкладками:** `initSwipeNav()` на `.dash-content` — touchstart/move/end, порог 60px,
жест засчитывается только если горизонтальная составляющая явно больше вертикальной (не мешает
скроллу). Порядок вкладок берётся из ВИДИМЫХ `.view-btn` (питомец `display:none` — исключается
автоматически). Свайп НЕ зацикливается на первой/последней вкладке. `.dash-content` имеет
`touch-action: pan-y` — разрешает браузеру нативно обрабатывать только вертикальный скролл,
горизонтальный жест целиком на нашем JS (`preventDefault()` только когда жест распознан горизонтальным).

- **День** (`view-habits` → `#day-normal`): `renderDayView()`/`renderDashboardHabits()`.
  Строка = чекбокс + текст + (серия, моно-огонёк) + «⋯». `toggleHabit()` — XP без фарма
  (флаг `habit.xpDate` = дата начисления), пишет в `history`, обновляет колесо. Добавление
  `+ добавить привычку` (до 10) — инпут с `autocomplete="new-password"` (НЕ `"off"` — Chrome его
  игнорирует для полей, похожих на логин по эвристике; `new-password` уважает надёжнее) + уникальным
  `name` (иначе браузер предлагает сохранённый email/логин в это поле — было замечено юзером,
  дважды: первая попытка `autocomplete="off"` не помогла). Настройки: `openHabitSettings`/`saveSettings` — модалка с
  названием, триггером «после того как», напоминанием, **сферами колеса** (чипы), удалением.
  Удаление привычки И метрики идут через общий `confirmDialog`/`#confirm-modal` (стилизованная,
  не нативный `confirm`; `#confirm-modal{z-index:2700}` — поверх модалки настроек 2500/игр 2600).
  **Колесо жизни ПОД привычками** (без заголовка): `renderLifeWheel('day','life-wheel-day')`,
  `areaFractions()`, `lifeWheelSVG()` — заполняется автоматически от выполнения привычек,
  привязанных к сферам.
- **Месяц** (`renderMonthView`): тепловая карта (внутри клеток — сокр. день недели чёрным,
  исчезает при заливке), редактируемая задним числом, серии, **месячное колесо**, график
  настроения/сна (`drawMonthMoodSleep`). Клик по клетке СЕГОДНЯ даёт XP (как `toggleHabit`:
  общий `habit.xpDate`, один раз/день, без фарма); прошлые дни редактируются БЕЗ XP.
  В psycho mode → `renderPsychoMonth`: сводка метрик (сумма за месяц / дневная цель × дней),
  БЕЗ графика настроения/сна (он только в обычном «Месяце»).
  **Мобильная адаптация тепловой карты (@media max-width:600px):** вместо сжатия всех ~30 дней в
  экран — горизонтальный скролл, видно ровно 7 колонок (сегодня + 6 дней вперёд). `.hm-row`
  становится `flex-direction:row` (название слева, дни справа скроллятся); ширина клетки (`--cell-w`)
  считается в JS: `(document.documentElement.clientWidth - 130) / 7` (130 = 44 паддинг #dashboard-screen
  [22px×2] + 80 колонка названия + 6 зазор) — НЕ `100vw` в CSS, см. ГРАБЛИ про iOS Safari в §8.
  Если поменяешь паддинг мобильного `#dashboard-screen` — поправь и эту константу (130), иначе
  колонок в видимой области станет не 7. Для ТЕКУЩЕГО месяца при рендере сразу `hm.scrollLeft`

  (смена ширины вьюпорта) ширина клетки НЕ пересчитывается заново, пока не откроешь вкладку повторно
  (мелкий известный недостаток, не фиксили — редкий сценарий).
  **ГРАБЛИ:** `position:sticky` для «прилипающей» колонки названия НЕНАДЁЖЕН тут — работает первые
  ~100-150px скролла, потом слетает (проверено эмпирически, изолированный sticky-тест вне этой
  структуры работал нормально — баг именно в связке calc()-ширины колонок + вложенный flex в этом
  окружении, причина не выяснена до конца). Прилипание сделано вручную через JS: `syncHeatmapHeads()`
  в `renderMonthView` — на `hm.onscroll` сдвигает все `.hm-row-head` через `transform:translateX(scrollLeft)`,
  компенсируя скролл. Если захочешь вернуться к sticky — сначала протестируй на реальном диапазоне

### ⚠️ ГРАБЛИ: горизонтальное переполнение на iOS Safari (реальный баг, юзер прислал скриншоты)

реального видимого вьюпорта (известная особенность движка). Ловили это в тепловой карте «Месяца»
(`.hm-cells` ширина колонки) — заменили на JS-вычисление через `document.documentElement.clientWidth`
(надёжно везде), см. `--cell-w` в `renderMonthView`. Если где-то ещё понадобится «ширина экрана» в
CSS — либо `100%` от корректно ограниченного предка, либо `clientWidth` из JS в CSS-переменную.

## 20. Family-план доведён до рабочего состояния (реальный доступ семье) + «добавить часы сна» в чек-апе (01.08.2026)

**Family-план был неполным.** Схема (`db/phase5_telegram.sql`) с самого начала предусматривала

человек, а доступ получал только он сам.

**Главное — синхронизация ВСЕГО прогресса между устройствами (была самая крупная и рискованная
часть).** До этой сессии в облако синкалась только сводка для семьи (`stats`) — привычки, история
выполнения, чек-апы, питание и метрики Pro mode жили ТОЛЬКО в localStorage конкретного браузера;
смена устройства = потеря прогресса (юзер это и заметил: «при открытии с компа нет того, что отметил
на телефоне»). Решение — `db/phase11_app_state_sync.sql`: новая `public.app_state(user_id pk, data
jsonb, updated_at)`, RLS «только своё», весь `dashState` зеркалится туда ОДНИМ jsonb-блобом (без
нормализации на таблицы — юзер один, конфликтов «два разных человека одновременно» не бывает).
`updated_at` всегда ставит сервер через триггер (`set_app_state_updated_at`), не клиент — иначе
last-write-wins зависел бы от точности часов конкретного устройства.

Клиентская логика — `auth.js`: `window.syncAppState(state)` (дебaunс 1.5с, вызывается из
`saveProgress()` в habbittracker.js тем же паттерном, что уже был у `window.syncStats`) →
`pushAppState()` делает upsert и запоминает СЕРВЕРНЫЙ `updated_at` в
`localStorage.habbittracker_local_synced_at`. При входе `loadAppState()` (вызывается из `refresh()`)
сравнивает облачный `updated_at` с этой меткой: если в облаке свежее — `window.applyCloudState(data,
updated_at)` (определена в habbittracker.js) бэкапит текущий localStorage в
`habbittracker_progress_backup`, кладёт новые данные и делает `location.reload()` — так гарантированно
проходят все миграции/дефолты `init()`, без дублирования этой логики. Если в облаке пока пусто
(первое включение синка) — просто заливаем то, что есть локально, ничего не перезаписывая.

**Это же закрывает и «обновление в реальном времени»**, о котором отдельно просил юзер: `auth.js`
подписывается на `postgres_changes` (Supabase Realtime) на свою же строку `app_state` — правка на
одном устройстве прилетает на другое через `applyCloudState`/`reload()` без ручного обновления
страницы. Echo своих же изменений подавляется сравнением `updated_at` события с
`habbittracker_local_synced_at`. Реализация через `location.reload()`, а не точечный ре-рендер
конкретных вьюх — осознанное упрощение: гарантированно корректно для ЛЮБОЙ активной вкладки
(Задачи/Чек-ап/Питание/графики), тогда как ручной ре-рендер каждой вьюхи в памяти был бы кратно
сложнее и рискованнее почти без выигрыша (обновление редкое — только когда правда пришли данные с
другого устройства).

**Вечерняя сводка дня в боте** — читает уже синхронизированный `app_state` (без Фазы 11 сервер
вообще не видел бы прогресс). Новая функция `send-daily-summary` + `db/phase12_daily_summary.sql`
(`get_and_mark_due_summaries`, тот же паттерн FOR UPDATE SKIP LOCKED, что и у Фазы 8, своё окно
22:45–22:59 по локали юзера и своя колонка `last_summary_sent_local_date` — не путать с
напоминанием в 20:00). Собирает читаемый текст из СЕГОДНЯШНЕГО среза данных: отмеченные привычки,
числовые метрики Pro mode (с их же названиями/единицами — юзер сам их придумывает, поэтому это
формат «название: значение», а не глагольная фраза вроде «скурил 3 сигареты» — сгенерировать

сна/подъёма, добавленные часы, 4 шкалы), питание (время+что ел по приёмам), событие дня. Если за

## 23. Гонка при первом включении синка перезаписала реальный прогресс юзера — добавлена кнопка восстановления (03.08.2026)

Ровно тот риск, о котором предупреждал в §21 (last-write-wins), реализовался на практике в первый
же день: юзер прогнал SQL/cron, затем открыл приложение сначала не на телефоне (видимо, в браузере,
где данных было мало/не было), а потом на телефоне — телефон увидел, что в облаке «более свежая»
запись (свежая по ВРЕМЕНИ синхронизации, не по объёму данных) и подтянул её, перезаписав реальный
прогресс. Данные не потеряны физически: `window.applyCloudState` (см. §21) перед перезаписью сам
сохраняет предыдущий `localStorage.habbittracker_progress` в `habbittracker_progress_backup` — но
никакого способа вернуть его юзер не имел (кнопки не было, консоли разработчика на телефоне тоже).

Добавлено: `checkForBackupRestore()` — вызывается в `init()` сразу после `showDashboard()` для
вернувшегося юзера. Если `habbittracker_progress_backup` существует и отличается от текущего
`habbittracker_progress` — показывает нижний баннер (`.restore-backup-bar`) с двумя кнопками:
«Восстановить» (кладёт бэкап на место активного сейва, ставит флаг
`habbittracker_needs_push_after_restore` и делает `location.reload()`) и «Не нужно» (просто чистит
бэкап). После перезагрузки `init()` видит флаг, сразу же вызывает `saveProgress()` — это
проталкивает ВОССТАНОВЛЕННЫЕ данные в облако, перекрывая чужую версию, которая туда попала по
ошибке (иначе следующий заход/реалтайм-событие снова притащили бы её обратно).

Проверено в браузере (фейковый Telegram-контекст, `?forcetg=1`, откачен после проверки):
искусственно посеяны два разных набора данных под ключами `habbittracker_progress` (текущий,
«чужой») и `habbittracker_progress_backup` («свой», реальный) — баннер появился, кнопка
«Восстановить» вернула реальные данные, бэкап-ключ и флаг корректно очистились после. `node
--check` — чисто.

**Юзеру нужно сделать прямо сейчас, на телефоне** (где реальный прогресс, предположительно, всё ещё
цел в `habbittracker_progress_backup`): дождаться, пока GitHub Pages подхватит этот пуш (~30-60 сек
после `git push`), затем **полностью закрыть и заново открыть Mini App в Telegram** (не просто
свернуть — Mini App любит кешировать старую версию, см. «грабли» про кеш в HANDOFF ранее). Если
бэкап на месте — внизу экрана появится баннер с кнопкой «Восстановить». Если баннера НЕТ — либо
кеш ещё не обновился (подождать/перезайти ещё раз), либо (маловероятно, но возможно) бэкап уже был
перезаписан повторной синхронизацией — тогда физически восстанавливать нечего, разбираться отдельно.

## 42. «Семья» была видна только одной стороне связи — юзер репортил «пропал член семьи»
## (08.08.2026)

Расследовал жалобу «пропал член семьи из профиля» напрямую в БД (`supabase db query --linked`,
проект `sgsqgpthfufbbyukifbn` — CLI уже был залинкован).
В `invites` реально была всего одна строка (`from_id` = юзер, который ввёл чужой код, `to_id` =
владелец кода), `status='accepted'`, ничего не удалено, аккаунты целы (`deleted_at` пуст у всех
трёх юзеров в базе). Значит потери данных не было — баг был в клиенте.

**Причина**: `loadFamily()` в `auth.js` (Фаза 3) читала `invites` ТОЛЬКО с `to_id = я` — то есть
человек видел в «Семье» только тех, кто ввёл ЕГО код. Если юзер сам вводит чужой код (он —
`from_id` в строке), связь целиком оседает на профиле ДРУГОЙ стороны — у него самого список
навсегда пуст, хотя `are_friends()`/начисление доступа за Family-план (Фаза 9,
`revoke_family_access`) уже были симметричны и работали с обеих сторон. Юзер это увидел как
«человек пропал», хотя формально он никогда не появлялся с ЕГО стороны экрана.

**Исправление**: `loadFamily()` теперь читает `invites` по `from_id=я OR to_id=я` и схлопывает
обе строки-направления в единый список по `counterpart` (собеседнику) — семья теперь видна
ОБЕИМ сторонам. Отдельно остался счётчик рефералов (`invitedFriendsCount`, бонусные дни за Фазу
7) — он специально считает только `to_id=я` (кто использовал МОЙ код), схлопывать с обратным
направлением было бы неправильно (не реферал, если это Я кого-то пригласил).

Кнопки «Добавить/Удалить из семьи» раньше работали через прямой `update` таблицы `invites`,
разрешённый RLS-политикой только для `to_id` — с обратной стороны (`from_id=я`) кнопка молча
проваливалась бы (RLS просто не даёт затронуть 0 строк, без ошибки). Добавил
`db/phase16_mutual_family.sql` — SECURITY DEFINER функция `set_family_status(row_id, new_status)`,
пускает менять статус любую из сторон связи (`from_id=auth.uid() or to_id=auth.uid()`), но только
сам `status`, не `from_id`/`to_id` (в отличие от расширения RLS-политики UPDATE, которое позволило
бы клиенту переписать `from_id`/`to_id` на что угодно через `WITH CHECK`). Миграция задеплоена
сразу в БД через `supabase db query --linked -f db/phase16_mutual_family.sql` (не только
сохранена в репо — проверено `select proname from pg_proc where proname='set_family_status'`,
функция реально создана).

Для pending-заявки, отправленной МНОЙ (я ввёл чужой код, жду подтверждения владельца) — кнопки
больше нет (принять свою же заявку нельзя), вместо неё текст «ждём подтверждения»
(`.fam-fam-waiting`, добавлен в `habbittracker.css`). Принять заявку по-прежнему может только
`to_id` (владелец кода) — это не баг, а сама механика подтверждения из `send_invite`.

Не проверено вживую в браузере — та же Telegram-only причина, что в §38–41. Логику проверил
напрямую в БД: у единственной существующей связи (`from_id`=юзер `313957169`, `to_id`=Дарья,
accepted) новый запрос `from_id=я OR to_id=я` теперь возвращает эту строку для ОБЕИХ сторон — с
`313957169` она раньше не показывалась вообще. `node --check auth.js` — чисто.
`?v=35` → `?v=36` (auth.js), `?v=37` → `?v=38` (CSS, добавлен `.fam-fam-waiting`).
